# SynCode Hermes 智能体平台面试问答

> 使用方式：先掌握“项目总述”，再按面试官追问选择答案。回答时应使用“我为什么这样设计、具体怎么做、解决了什么风险”的顺序。不要宣称尚未完成的生产部署和线上指标。

## 1. 项目总述

### 30 秒版本

我基于 Hermes 做了一套适合多用户教育平台的 Agent 基础设施。第一部分是 Skill 演化：用 Profile 隔离个人 Skill，通过 Elasticsearch 的 BM25、Dense Vector 和 RRF 发现跨用户共性，再经过 LLM 泛化和管理员审核发布为只读平台 Skill。第二部分是学习记忆：把提交和考试投影成事件、经历、模式和知识状态，通过 Hermes MemoryProvider 在每轮推理前自动召回。第三部分是执行安全：服务端固定只开放 `memory + skills + syncode`，其中 `skills` 只允许列出和读取 Skill；用户代码仍然进入判题沙箱，Hermes 不接触宿主机命令执行。

### 2 分钟版本

项目的出发点是，Hermes 原本具备 Agent Loop、自动选择 Skill、后台复盘和长期记忆，但是直接放进多用户学习平台会有三个问题：不同用户的经验可能互相污染，个人经验无法有治理地变成平台公共能力，普通对话记忆也无法准确表达持续变化的做题和知识状态。

我先把每个用户映射为独立 Hermes Profile。Profile、会话、个人 Skill 和记忆按用户隔离，身份只能由服务端登录态推导。个人 Skill 允许 Hermes 和用户持续修改，但每次变化都会形成不可变版本，可以归档、恢复和回滚。

然后我实现了平台 Skill 演化。系统将 Skill 的简介、分类和完整内容写入 Elasticsearch，同时做 BM25 和 Dense Vector 检索，再用加权 RRF 融合。相似 Skill 必须来自不同用户并互为近邻，默认至少三个独立用户才能形成候选。LLM 只负责把脱敏样本泛化为草稿，管理员审核后才能发布。发布后从 Hermes 的 `skill_view` 事件记录真实使用量，低频 Skill 进入人工复审。

学习记忆方面，我把提交和考试投影为 Event、Episode 和 Pattern，再按知识点计算掌握度、置信度、趋势和复习优先级。它不是模型主动调用的 MCP 召回工具，而是接入 Hermes MemoryManager 的 Provider，在每轮主要推理前自动注入相关记忆。MCP 只在需要核实时展开证据。

安全上，Profile 只启用 `memory + skills + syncode`，并在镜像构建时校验 `skills` 只能包含 `skills_list` 和 `skill_view`，不暴露 terminal、execute code 和 file 等工具。用户代码继续走受限判题容器。这样保留了 Hermes 的自主规划能力，同时把身份、数据和执行权限控制在服务端。

## 2. 架构与边界

### Q1：为什么选择 Hermes，而不是自己实现 Agent？

Hermes 已经有成熟的 Agent Loop、Skill 自动选择、`background_review`、`skill_manage`、会话和记忆机制。自己再做一套意图识别和工具循环会产生两个控制中心，导致会话、工具调用和记忆归属不一致。我的工作重点是扩展 Hermes 缺少的多用户隔离、教育业务记忆、Skill 治理和权限边界。

### Q2：这个项目中哪些是 Hermes 原生能力，哪些是你实现的？

Hermes 原生负责推理循环、自动选择和加载 Skill、后台复盘、会话以及 MemoryManager。我实现的是服务端 Profile 身份映射、个人 Skill 版本和来源治理、跨用户相似发现、平台晋升审核、使用统计、学习记忆投影、Memory Provider 接入、MCP 证据工具以及工具权限限制。这样可以清楚区分框架能力和业务平台能力。

### Q3：为什么不做自己的意图识别或 Context Router？

因为 Hermes 已经能结合模型上下文选择 Skill 和工具。再训练或编写一套意图分类，不仅会增加误判点，还会把 Agent 的规划权拆散。我只把可信业务事实通过核心记忆提供给 Hermes，把可执行能力通过结构化工具提供给 Hermes，让它继续负责推理和规划。

### Q4：一次用户请求的完整链路是什么？

Next.js 先从登录态解析用户 ID，再生成 `syncode-u<id>` Profile 并代理到 Hermes。Hermes 的 MemoryManager 在首个主要模型调用前执行 SynCode Provider 的 `prefetch()`，召回相关做题记忆和学习状态并注入上下文。之后 Hermes 自己选择 Skill 和 MCP 工具，通过 SSE 返回结果。若出现真实 `skill_view` 事件，代理异步记录一次幂等使用事件。

## 3. 多用户和 Skill 治理

### Q5：用户需要自己指定调用哪个 Skill 吗？

不需要。正常链路是 Hermes 根据任务自动判断，并通过 `skill_view` 加载 Skill。用户可以在工作台管理自己的 Skill，但不会在每次对话中输入 Skill 名称。系统统计的也是 Hermes 的真实 `skill_view` 事件，而不是用户文本。

### Q6：为什么允许用户修改个人 Skill？

个人 Skill 本来就是用户和 Agent 共同积累的个性化经验，禁止修改会让错误步骤和过时偏好永久存在。关键不是禁止修改，而是限制作用域并保存不可变版本：用户只能修改自己的个人 Skill，每次修改形成新版本，可以审计和回滚；平台 Skill 对普通用户只读。

### Q7：怎样防止 A 用户访问 B 用户的 Skill？

浏览器不能提交 Profile，Next.js 根据登录态生成 Profile；Profile Provisioner 再校验 `userId` 和 `syncode-u<id>` 一致。文件路径拒绝符号链接和路径逃逸，数据库查询始终携带 `scope=personal` 和 `owner_user_id`。MCP 身份也从 Hermes 注入的 Profile Header 反解，不接受模型传入用户 ID。

### Q8：怎样判断一个 Skill 真的是用户沉淀的，而不是系统内置的？

扫描时同时读取 Hermes 的 `.bundled_manifest`、Hub 的 `.hub/lock.json` 和 `.usage.json` 来源账本。内置和安装型 Skill 不进入个人经验治理。来源文件损坏时，本次同步会失败并保留最后有效状态，不会把未知来源的数据送去平台晋升。

### Q9：个人 Skill 如何版本化？

系统对整个 Skill 包计算内容哈希。哈希未变化就不新增版本；变化后生成新的补丁版本，并保存正文和包快照。回滚不会修改旧版本，而是将旧快照恢复到当前目录，再生成一个新版本，因此历史始终是追加和可追溯的。

### Q10：平台 Skill 是怎样从个人 Skill 中产生的？

治理心跳同步所有当前有效个人 Skill，脱敏后建立 BM25 和向量索引。系统寻找跨用户互为近邻的 Skill，并对相似图求连通分量，默认至少三个独立用户才能生成候选。LLM 将候选样本泛化成公共草稿，管理员查看匿名证据后批准、编辑或驳回。只有批准后才写入只读平台目录。

### Q11：这不就是一个 RAG 系统吗？

RAG 解决的是一次回答如何召回知识，这里治理的是会改变 Agent 后续行为的可执行经验资产。Skill 有所有者、不可变版本、来源、发布权限、使用统计和生命周期；它还要经过跨用户发现、泛化和人工审核。混合检索只是候选发现的一个环节。

### Q12：为什么选择 Elasticsearch？

这个场景同时需要 BM25 全文检索、Dense Vector KNN、用户和版本等结构化过滤。Elasticsearch 可以在一个索引中承载这些检索需求，工程上比维护两套独立搜索系统简单。MySQL 仍保存版本、审核和发布事实，Elasticsearch 只是可重建的检索层。

### Q13：为什么不只用向量检索？

向量检索擅长找到表达不同但含义相似的内容，却可能弱化算法名、异常名、工具名和语言关键字。BM25 对精确术语更稳定。两路结果用 RRF 按排名融合，可以同时保留词法和语义信号，也避免直接相加不同量纲的原始分数。

### Q14：为什么要把 Skill 正文也放进索引？

简介通常只描述“什么时候使用”，真正决定两个 Skill 是否可复用的是正文里的步骤、约束、工具顺序和异常处理。因此索引覆盖 description、category 和完整 `SKILL.md`，只是在 BM25 中给 description 更高权重。

### Q15：怎样保证不是一个用户创建很多相似 Skill 后触发晋升？

索引中保存带服务端密钥的 `owner_hash`。建边时排除同一 owner，候选门槛统计 distinct owner，默认至少三个独立用户。即使一个用户创建十个相似 Skill，也只能贡献一个用户来源，不能单独形成平台候选。

### Q16：怎样降低错误聚类？

我设置了多层约束：排除同用户和完全相同内容，设置 RRF 阈值，要求 A 和 B 互为近邻，再要求至少三个独立用户。检索结果仍只生成候选，LLM 泛化后还要管理员查看脱敏来源并审核，因此错误匹配不会直接污染平台。

### Q17：个人 Skill 更新以后，旧候选怎么办？

候选标识由成员的 `skill_id@version` 集合计算。内容变化后会产生新版本和新的 Cluster Key，可以进入下一轮审核。旧候选继续保留原来的通过或驳回记录，用于审计，不会被覆盖。

### Q18：为什么 LLM 不能直接发布平台 Skill？

平台 Skill 会影响所有用户，而个人样本可能含有隐私、错误步骤或提示注入，LLM 泛化也可能遗漏关键约束。因此模型只负责提高整理效率，发布权限必须留给管理员。模型输出还要经过 JSON、Frontmatter、名称和包大小校验。

### Q19：为什么低频 Skill 不直接自动删除？

调用少不一定没有价值，例如罕见编译错误或特殊竞赛规则就是低频长尾能力。系统只根据发布时间和近 30 天调用量创建复审任务，由管理员结合业务价值决定保留或归档，避免不可逆误删。

### Q20：Skill 使用量是怎么统计的？

Next.js 在代理 Hermes SSE 时解析 `tool.started` 事件，只有工具名是 `skill_view` 才记录调用。事件 ID 作为幂等键，SSE 重连不会重复计数。遥测只保存 Skill、Run、Session 和时间等治理信息，不采集完整回答或用户代码，而且遥测失败不会影响用户对话。

## 4. 学习记忆

### Q21：为什么学习记忆不能只做成 MCP 工具？

如果做成 MCP，模型必须先意识到自己需要历史信息，再主动调用工具；一旦漏调，个性化推理就会缺少关键事实。现在学习记忆接入 Hermes MemoryManager 的 Provider，在每轮主要推理前自动 `prefetch`，所以它属于核心记忆召回。MCP 只在需要核实结论时展开证据。

### Q22：Hermes 原生记忆和学习记忆怎样配合？

Hermes 原生记忆保存目标和偏好，例如用户希望先提示再给答案。SynCode 学习记忆保存可以由提交和考试证明、并会不断变化的事实，例如二分查找近期连续超时。前者回答“用户希望怎样学”，后者回答“用户实际上学得怎样”。动态事实优先于旧的文字总结。

### Q23：为什么把做题记录建模为事件、经历和模式？

一次提交只能说明一个瞬间；同一道题连续尝试形成的经历可以表达解决过程；多个经历中重复出现的问题才有资格成为模式。三层模型既保留原始证据，又能压缩长期历史，避免把几百条提交直接塞进上下文。

### Q24：Episode 是怎样划分的？

系统按题目和考试范围分组，同一组内相邻提交间隔不超过 24 小时就视为一次连续学习经历。Episode 记录提交次数、结果路径、最终结果和错误类型。这个规则明确且可重建，后续也可以根据真实数据调整会话间隔。

### Q25：错误模式怎样避免永久给用户贴标签？

模式只观察最近 90 天，并要求相同知识点和错误类型至少出现两次。最后一次错误之后，如果出现两次没有该错误的干净通过，状态变为 `improving`；达到五次后变为 `resolved`，置信度也会衰减。因此旧错误会被新证据修正。

### Q26：掌握度是大模型打分的吗？

不是。当前掌握度是可解释的确定性计算。每次 Episode 的质量会考虑是否通过、提交次数和错误数量，再按时间衰减和题目难度加权。证据不足时分数向 50 收缩，避免一题定结论。LLM 只消费结果并生成教学建议，不参与事实分数计算。

### Q27：置信度、趋势和复习优先级怎么计算？

置信度由独立题目数和 Episode 数通过饱和函数计算，题目越多越可信。趋势比较最近三次经历和前一组三次经历的平均质量，差值超过阈值才判断上升或下降。复习优先级综合弱项程度、距离上次练习的遗忘程度和低置信度，下降趋势再增加优先级。

### Q28：怎样保证学习记忆是最新的？

每次核心召回前会同步当前用户的提交和考试数据。系统为每个用户保存源数据指纹；指纹不变就复用现有投影，变化时才重建。知识状态还保存计算模型版本和日期相关信息，使规则升级或时间推进时可以按需刷新。

### Q29：Elasticsearch 挂了，学习记忆还能用吗？

可以。Elasticsearch 正常时使用 BM25、Dense Vector 和 RRF 做多层召回；异常时回退到数据库的结构化检索，并显式标记 `database_fallback`。降级会损失部分语义召回质量，但不会让核心业务完全不可用。

### Q30：怎样追溯 AI 使用的记忆依据？

每条 Event、Episode、Pattern 和知识状态都有稳定 ID，并保存到原始提交、考试或下级记忆的证据关系。核心召回先提供摘要和 ID；Hermes 需要核实时，再调用两个只读 detail 工具展开证据。这样可以解释结论来源，也控制默认上下文大小。

### Q31：为什么不保存完整提交代码到记忆索引？

完整代码体积大、隐私风险高，而且长期记忆真正需要的是题目、结果、错误类型、时间和变化趋势。系统只保存必要摘要和证据引用，需要查看当前代码时再通过当前题目上下文获取。这符合数据最小化，也减少旧代码误导模型。

## 5. 安全、可靠性与工程实现

### Q32：用户让 Hermes 执行系统命令怎么办？

模型只能调用服务端注册给它的工具。SynCode Profile 当前只启用 `memory + skills + syncode`，其中 `skills` 只包含 `skills_list` 和 `skill_view`；没有 terminal、execute code、process manage、file 或 browser。用户即使在提示词或个人 Skill 中要求执行命令，也无法获得一个不存在的工具。

### Q33：如果以后需要让 Agent 运行代码怎么办？

我会提供结构化的判题沙箱工具，参数限定为语言、源码和公开输入，由服务端创建一次性受限任务。不会提供 `run_shell(command)`，也不会把 Docker Socket 暴露给 Hermes。这样 Agent 能完成业务动作，但无法把自然语言变成任意宿主机命令。

### Q34：提示注入怎样处理？

个人 Skill 和学习记录都被当作不可信数据。Memory Provider 明确告诉模型历史文本只是数据，当前代码和当前判题结果优先。治理 LLM 的系统提示禁止执行样本中的指令，输出还要经过结构校验。更关键的是，提示注入不能突破服务端的身份和工具白名单。

### Q35：平台 Skill 发布时，文件成功但数据库失败怎么办？

发布前保存原平台包，先通过临时目录完成校验和原子替换，再写数据库事务。如果数据库失败，就删除新包并恢复旧包。归档也执行反向补偿。文件系统和 MySQL 不能共享事务，所以这里使用显式补偿保证最终一致。

### Q36：为什么遥测失败不阻断 Agent 回答？

使用统计属于治理旁路，不是用户当前任务的必要步骤。为了统计阻断回答会降低核心可用性。因此遥测使用短超时和 Best Effort 写入，失败后只影响本次统计；版本、发布和审核等关键状态仍使用事务和审计。

### Q37：治理心跳并发执行会怎样？

服务使用非阻塞锁保证同一实例一次只有一个治理心跳。新的手动或定时任务发现已有任务运行时会立即失败，避免同时刷新索引、重复创建候选或相互覆盖生命周期任务。生产上还可以进一步增加分布式锁来支持多副本调度。

### Q38：这个设计怎样扩展到更多用户？

在线请求主要增加一次受上限约束的记忆召回；重计算放在增量投影和后台心跳中。Skill 索引只保存当前有效版本，历史版本留在 MySQL。规模继续增长时，可以按用户分片投影任务、批量生成 Embedding、使用任务队列执行心跳，并将单机锁升级为分布式租约。

## 6. 项目价值与复盘

### Q39：这个项目最有技术含量的部分是什么？

技术深度不在于调用了大模型，而在于把非结构化、会变化、带用户归属的 Agent 经验变成可治理的后端资产，同时把动态学习事实接入 Agent 的核心记忆。这里同时处理了多租户身份、混合检索、图聚类、可解释状态计算、提示注入、人机审核和跨存储一致性。

### Q40：你做过的最关键取舍是什么？

第一，不重新实现 Agent Loop，而是扩展 Hermes 的边界。第二，个人 Skill 允许演化，但平台 Skill 必须只读并人工审核。第三，学习记忆进入核心召回，MCP 只展开证据。第四，低频只触发复审，避免系统自动做不可逆决策。这些取舍都在自主性、可靠性和治理责任之间做平衡。

### Q41：当前系统还有什么不足？

核心代码和测试闭环已经完成，但还没有真实生产数据下的检索指标、知识状态校准和端到端延迟。Next.js Run 代理还应进一步收紧请求字段白名单，生产容器也可以增加 capability drop、no-new-privileges 和独立网络。面试中我会明确区分“已实现”和“已在线验证”。

### Q42：你会怎样评估 Skill 发现质量？

先从真实候选中抽样，由管理员标注两个 Skill 是否属于同一可复用能力，形成 pair 和 cluster 两级集合。离线评估近邻 Precision@K、Recall@K、聚类纯度和候选覆盖率；在线观察管理员通过率、驳回原因、平台 Skill 的独立调用用户数和发布后留存使用率。阈值调整不能只看召回率，还要控制管理员审核成本。

### Q43：你会怎样评估学习记忆？

分三层评估。召回层检查相关事实是否被找回以及是否发生跨用户泄漏；状态层比较掌握度、趋势与后续答题结果的校准关系；Agent 层做带记忆和不带记忆的对照，观察建议相关性、证据正确率和复习后正确率。不能只让另一个 LLM 给答案打分。

### Q44：简历中的量化数据应该怎么写？

没有线上数据时，只写可复现的工程规模，例如两级 Skill、三层学习记忆、双路检索、独立用户门槛、降级策略和自动化测试，不虚构提升百分比。上线后再补候选审核通过率、召回 P95、平台 Skill 覆盖用户数、记忆召回成功率和复习效果。业务指标必须来自真实监控或实验。

### Q45：如果让你重新做一次，会优先改进什么？

我会优先完成真实环境验收和可观测性：建立 Skill 相似标注集，校准 RRF 和聚类阈值；对知识状态做后验校准；补齐 Provider 延迟、降级率和跨用户安全指标；再收紧 Run 代理请求协议和容器权限。因为当前最大的未知已经不是功能是否存在，而是真实数据下的质量和运行边界。

## 7. 容易说错的地方

| 不准确说法 | 建议说法 |
| --- | --- |
| 用户在对话中手动调用 Skill | Hermes 根据上下文自动选择 Skill，用户只管理个人 Skill |
| 学习记忆通过 MCP 主动召回 | Memory Provider 在 Hermes 核心召回阶段自动预取，MCP 只展开证据 |
| 向量数据库自动判断公共 Skill | BM25 和向量只发现候选，还要跨用户聚类、LLM 泛化和管理员审核 |
| 低频 Skill 会被自动删除 | 低频只进入人工复审，管理员决定保留或归档 |
| 掌握度由大模型判断 | 掌握度由可解释规则计算，LLM 消费结果生成建议 |
| Docker 能完全解决 Agent 安全 | 当前直接不暴露通用执行工具，用户代码走受限判题沙箱 |
| 已经获得线上效果提升 | 当前是可演示、可联调的代码闭环，真实生产指标仍待验收 |

## 8. 背诵提纲

```text
一个 Agent Loop：Hermes
两个 Skill 层级：个人、平台
两个业务记忆域：做题、学习状态
三层做题记忆：Event、Episode、Pattern
两路检索：BM25、Dense Vector
一套融合：加权 RRF
四道候选门槛：跨用户、去副本、互为近邻、至少三人
一条发布边界：LLM 生成候选，管理员负责发布
一个安全原则：服务端固定身份和工具权限
```

面试时最值得保留的一句话：

> 我没有重新实现一个 Agent，而是围绕 Hermes 建立了多用户经验治理、核心学习记忆和最小工具权限，让 Agent 的自主能力能够安全地进入真实教育系统。
